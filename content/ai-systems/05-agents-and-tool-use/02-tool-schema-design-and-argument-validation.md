## The tool definition is a prompt, not just an API contract

A tool schema (name, description, JSON Schema for parameters) is sent to the model as part of the context window on every call. The model doesn't introspect your backend code — it decides whether and how to call a tool purely from the schema's text. That means schema quality directly determines call accuracy: a vague `description` field produces vague, wrong, or hallucinated arguments just as reliably as a vague prompt produces a vague answer. Treat every field name, description, and enum as something the model has to disambiguate under uncertainty, not as internal documentation nobody reads.

## Naming and description discipline

- **Tool names should be verb-first and unambiguous** (`search_flights`, not `flights` or `handler_1`). Models pick tools by matching intent to name+description; two similarly-named tools with overlapping descriptions (`get_user` vs `fetch_user`) measurably increase misrouting.
- **Descriptions should state preconditions and when *not* to use the tool**, not just what it does. "Use this to look up a user by internal ID; do not use for email lookups — use `find_user_by_email` instead" resolves ambiguity that a one-line summary can't.
- **Every parameter needs its own description**, especially units, formats, and defaults (`"date in YYYY-MM-DD, UTC"` beats `"date"`). Models frequently guess formats when they're unstated, and the guess is often locale-biased (MM/DD vs DD/MM).

## Constraining the argument space

JSON Schema gives you real leverage beyond prose:

- **Enums over free text** wherever the value space is closed. A `status` field defined as `enum: ["open", "closed", "pending"]` makes invalid values a schema-validation failure at generation time in APIs that support constrained decoding (OpenAI's `strict: true` mode, Anthropic's structured outputs), rather than a runtime error after the call.
- **`required` vs optional fields** should reflect what the backend actually needs, not be relaxed "just in case" — every optional field is a decision point where the model can omit something load-bearing.
- **Nested objects over stringly-typed blobs.** A parameter typed as a free-form string that's secretly expected to contain JSON (`"filters": "{\"minPrice\": 10}"`) is a reliability trap; models frequently malform the inner JSON. Express it as a proper nested schema instead.
- **Keep the parameter count low.** Tools with 15+ parameters, most optional, see higher rates of argument omission and type confusion than tools decomposed into 2-3 narrower calls. If a tool has multiple near-independent "modes," consider splitting it into multiple tools.

## Validation is still mandatory at the boundary

Constrained decoding reduces malformed output; it does not eliminate the need for server-side validation. The model can still produce **semantically wrong but schema-valid** arguments — a syntactically correct date that's in the past for a future-booking API, an account ID that doesn't exist, a well-typed but out-of-range quantity. Validate every tool call against business rules before execution, exactly as you would validate a request from an untrusted HTTP client, because from the backend's perspective that's what it is: input generated by a probabilistic process, not a trusted caller. Return validation failures as structured tool-error results (not raw exceptions) so the agent loop can read the failure reason and retry with corrected arguments — this is what makes self-correction (see failure recovery) possible instead of just crashing the run.

## Versioning and drift

Tool schemas change as APIs evolve, but agents in production may have cached prompts, few-shot examples, or fine-tuned routing behavior built against an older schema shape. Renaming a parameter or changing an enum value is a breaking change for the agent the same way it is for a client library — bump the tool name or version it explicitly (`create_order_v2`) rather than silently mutating the schema underneath a name the model has already learned to trust from few-shot examples in the system prompt.

## Common mistakes

- **One mega-tool with a `mode` parameter** that fans out to a dozen unrelated behaviors internally — this defeats the model's ability to reason about which tool fits the task, since the model can only see one blob of a description covering everything.
- **Omitting units and defaults**, forcing the model to guess — silent unit mismatches (seconds vs milliseconds, USD vs cents) are a common source of production incidents.
- **Trusting schema validity as correctness.** A call that passes JSON Schema validation can still be logically wrong; skipping business-rule validation because "the schema already checked it" is a category error.
